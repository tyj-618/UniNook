# 开发与发布规范

本规范用于约束 UniNook 后续迭代，目标是在保持线上稳定的前提下持续交付可验证的版本。除紧急故障修复外，所有开发、发布和回滚均应遵守本规范。

## 1. 版本管理原则

- `main` 始终保持可部署状态，只包含已经通过验证的代码。
- 大型需求不直接在 `main` 开发，必须从最新 `main` 创建独立功能分支。
- 线上部署必须对应一个明确的 Git 提交；稳定发布后必须创建版本标签。
- 每个版本只解决一个主题，避免将新功能、重构和不相关体验优化混入同一版本。
- 新想法先进入需求池，完成优先级评估后再进入版本计划。

## 2. 分支规则

| 场景 | 分支命名 | 示例 |
| --- | --- | --- |
| 稳定线上代码 | `main` | `main` |
| 新功能 | `feature/<topic>` | `feature/admin-console` |
| 缺陷修复 | `fix/<topic>` | `fix/question-notice` |
| 文档维护 | `docs/<topic>` | `docs/operations-guide` |

开始新需求前执行：

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/<topic>
```

分支完成后，应先完成本地验证，再合入 `main`。不在未验证的功能分支上部署生产环境。

## 3. 提交规则

一次提交只表达一个可独立理解、可回退的改动。提交信息采用以下格式：

```text
<type>: <简洁的业务结果>
```

可用类型：

| 类型 | 使用场景 |
| --- | --- |
| `feat` | 新增用户或管理能力 |
| `fix` | 修复缺陷或线上问题 |
| `docs` | 仅文档变更 |
| `test` | 增加或调整测试 |
| `refactor` | 不改变外部行为的代码整理 |
| `chore` | 配置、依赖或构建维护 |

示例：

```text
feat: add moderation dashboard
fix: remove question records when post is deleted
docs: add production deployment guide
```

提交前必须检查：

```bash
git status
git diff --check
```

不得提交 `.env`、私钥、令牌、数据库备份、日志、构建产物、用户上传文件或临时截图。

## 4. 需求分级与版本范围

| 优先级 | 定义 | 处理方式 |
| --- | --- | --- |
| P0 | 安全漏洞、数据损坏或全站不可用 | 立即处理并发布热修复 |
| P1 | 登录、发帖等核心流程严重受阻 | 当前修订版本优先修复 |
| P2 | 经验证有价值的体验或能力增强 | 纳入下一个小版本 |
| P3 | 创意、远期设想或高复杂度改造 | 记录在需求池，不承诺排期 |

版本计划开始前必须明确：目标、非目标、验收标准、数据与权限边界，以及回滚方式。未写明验收标准的需求不得进入开发。

## 5. 单个需求的交付流程

```text
需求说明
→ 验收标准
→ 数据、接口与权限设计
→ 功能开发
→ 自动化测试
→ 本地手工验收
→ 合入 main
→ 生产部署与线上验收
→ 文档与版本记录更新
```

涉及数据结构的变更必须提供可重复执行或明确顺序的迁移脚本；涉及权限的变更必须包含正反向授权测试；涉及删除操作的变更必须明确级联影响与恢复方案。

## 6. 发布与版本标签

采用语义化版本号：`v主版本.次版本.修订版本`。

- `v1.0.0`：首个正式可用版本。
- `v1.0.1`：不增加功能的缺陷修复或安全修复。
- `v1.1.0`：一个完整的小版本能力，例如管理员端。
- `v2.0.0`：产品定位、兼容性或架构发生重大变化。

发布步骤：

1. 在 `main` 上完成后端测试、前端检查和必要的手工验收。
2. 检查生产配置与密钥，确认不含示例密码和本地调试配置。
3. 部署到服务器，确认容器状态、健康检查、HTTPS 和核心业务链路正常。
4. 部署验收成功后，在对应的 `main` 提交上创建并推送标签：

```bash
git switch main
git pull --ff-only origin main
git tag -a v1.1.0 -m "Release v1.1.0"
git push origin v1.1.0
```

5. 在 GitHub Release 中记录版本范围、已知限制、验证结果和回滚目标。

标签只能代表已经部署并验收成功的稳定版本，不能提前标记尚未上线的提交。

## 7. 线上运行与问题处理

每次上线后的观察期不少于 3 天。每日检查：首页、登录、发帖、评论、通知等核心链路；应用健康状态；容器状态；服务器磁盘、内存与错误日志；数据备份状态。

线上问题先记录复现条件、影响范围和优先级。P0/P1 可中断当前计划；P2/P3 统一进入需求池，禁止在未评估时直接插入开发。

## 8. 回滚原则

- 每次生产部署都必须记录对应 Git 提交与版本标签。
- 若出现核心链路故障，优先回滚到上一个已验证标签，而不是在生产环境直接修改代码或数据。
- 数据迁移必须在发布前准备回退或补偿方案；对生产数据的手工操作必须先进行只读核验，并保留执行记录。
- 回滚完成后应重新执行健康检查和核心链路验收，并补充问题复盘。

## 9. 当前版本路线

- `v1.0.0`：校园社区核心闭环、生产部署、HTTPS 和首轮验收。
- `v1.1.0`：以管理员端与内容治理为唯一主题。
- 后续版本仅在稳定运行、需求价值明确后再排期；多问题、复杂社交关系、自动评估和大规模检索升级均保持在需求池中。
