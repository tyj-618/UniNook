# UniNook 问题追踪设计与开发路线

## 已确认的后续交互约束（2026-08-09）

- **评论问题统一聚合**：评论来源的问题追踪不另设孤立入口；在所属帖子的问题追踪区域展示入口、状态与候选答复摘要，并能准确定位到对应评论线程。这样用户先看到已有问题，再决定是否订阅，可减少重复提问。
- **作者识别**：帖子作者在自己帖子下发布的一级评论或二级回复，昵称旁统一显示“作者”标签；标签只代表该帖作者身份，不替代学校/校区标签。

## 1. 最终定位

### 1.1 一句话定义

**问题追踪**是一个将校园社区中尚未闭环的疑问，转化为可订阅、可协作求解、可验证并可沉淀的校园信息对象的能力。

它服务的对象不是“帖子更新”，而是附着在帖子或评论上的**待解决问题**。同一问题的提出者、回答者和有相同疑问的旁观者，可以围绕同一个问题协作，而不必反复翻找评论或重新发帖。

### 1.2 要解决的问题

校园论坛中的高价值内容常常没有自然闭环：

- 求助帖得到零散评论后，后来是否解决无人知晓。
- 评论区中出现新的疑问，感兴趣的用户只能手动反复查看。
- 有价值的答案被普通讨论淹没，后来人重复提问。
- 已解决的本地经验没有形成可被 AI 检索和引用的高质量结论。

问题追踪应让用户完成下面的路径：

```text
提出疑问 -> 聚合答复与资料 -> 确认可信结论 -> 通知所有订阅者 -> 沉淀为可检索知识
```

### 1.3 对 UniNook 的价值

1. **产品差异化**：从按地理范围浏览的校园论坛，升级为按校园范围协作解决问题的本地信息服务。
2. **用户效率**：一个用户获得结论后，所有订阅同一问题的人都能同步获得结果，无需重复寻找或重复提问。
3. **社区质量**：将零散评论中的有效信息结构化，减少信息流自然沉没带来的浪费。
4. **AI 数据质量**：RAG 可以优先检索已采纳、可追溯的结论和资料，而非仅检索未验证的评论文本。
5. **工程深度**：形成问题状态机、订阅关系、候选答复、反馈排序、异步通知、检索评测和 AI 辅助治理的完整后端闭环。

## 2. 命名与核心术语

| 场景 | 推荐文案 | 含义 |
| --- | --- | --- |
| 整体能力 | 问题追踪 | 面向产品、文档和简历的正式名称 |
| 发起者操作 | 发起问题追踪 | 将一条帖子或评论声明为待解决问题 |
| 旁观者操作 | 订阅答案 | 关注该问题的后续结论 |
| 回答者操作 | 作为答复发布 | 将自己的评论或回复提交为候选答复 |
| 发起者操作 | 采纳为结论 | 确认某个候选答复是当前最可信的结果 |
| 聚合入口 | 我的问题追踪 | 查看我发起、我订阅、等待我确认的问题 |

“蹲结果”可以作为轻量校园化文案或提示，不作为唯一正式动作；“踢”语义不够稳定，不作为数据模型或主要按钮名称。

## 3. 产品边界

### 3.1 MVP 支持的内容来源

- 帖子可以发起问题追踪。
- 仅一级评论可以发起问题追踪；二级回复只作为讨论补充或候选答复，避免形成多层问题树。
- 一个帖子或评论节点在 MVP 中最多关联一个问题，避免形成难以理解的多问题图结构。
- 普通帖子和普通评论保持原有行为，不会被强制加入追踪机制。

### 3.2 不在 MVP 中实现的能力

- 不允许任何用户直接向所有订阅者广播“结果”。
- 不让 AI 独立判断信息事实正确或自动采纳答案。
- 不引入用户关注、私聊、积分商城或复杂信誉体系。
- 不做跨校园范围泄露；AI 和发现层继续遵守校园可见范围。

## 4. 用户角色与主流程

### 4.1 发起者

发帖或评论时，用户可勾选“发起问题追踪”，并填写一段简短的“希望获得什么结果”。系统可从标题、正文或评论中预填建议，但最终由用户确认。

示例：

```text
原帖：逸夫馆晚上还有空座位吗？
追踪问题：今晚 20:00 后逸夫馆是否仍开放，是否需要预约？
```

发起者可：

- 查看候选答复与 AI 辅助资料；
- 标记候选答复为“采纳”“待确认”或“不相关”；
- 填写或确认最终结论；
- 确认最终有效答复，将问题标记为“已完成”；
- 删除自己发起的问题。

### 4.2 订阅者

任何有查看该内容权限的用户都可订阅答案。订阅者可：

- 接收已采纳结论、明确状态变化和必要的进展通知；
- 查看完整答复列表和引用来源；
- 对候选答复反馈“有帮助”或“不相关”；
- 在“我的问题追踪”的“进行中”和“已完成”中集中回访；
- 随时取消订阅；即使问题已完成，仍可新建订阅并立即获得结果。

默认不对每条候选答复发送强通知，避免高频讨论造成打扰。

### 4.3 回答者

用户回复一个开启追踪的问题时，可选择“作为答复发布”。该评论仍属于原始讨论链路，同时建立与问题的结构化关联。

回答者获得：

- 候选答复被查看、被采纳和被判定有帮助的反馈；
- 后续可展示的“被采纳答复数”等贡献记录。

### 4.4 AI 助手

AI 只做辅助，不替代事实判断：

- 在问题创建后，检索用户有权限访问的历史帖子、已采纳答案和资料库；
- 生成带来源引用的“AI 辅助参考”；
- 评估候选答复与问题的相关性、信息完整度、是否疑似跑题或广告；
- 为已采纳的答复和引用资料生成简短结论摘要。

AI 输出必须显式标记为“辅助参考”，并展示可跳转的来源；没有足够证据时明确说明，而不是补全猜测。

## 5. 问题与答复生命周期

### 5.1 问题状态

`UPDATED` 不是状态，而是一次事件。问题的稳定状态应为：

| 状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| `OPEN` | 等待答复或结果 | 订阅、提交候选答复、AI 检索 |
| `COMPLETED` | 发起者已确认最终有效答复 | 查看结果、继续订阅或取消订阅 |

状态事件包括：`QUESTION_CREATED`、`ANSWER_SUBMITTED`、`ANSWER_ACCEPTED`、`QUESTION_COMPLETED`、`QUESTION_DELETED`。

### 5.2 答复状态

| 状态 | 说明 |
| --- | --- |
| `PENDING` | 默认状态，等待提问者或社区反馈 |
| `ACCEPTED` | 被提问者采纳为当前结论 |
| `REJECTED` | 被提问者判定为不相关或不适用 |
| `HIDDEN` | 被管理员处理，或命中违规/垃圾信息规则 |

提问者拥有“采纳”的最终权力；订阅者的反馈影响排序，但不能替代提问者对事实结果的确认。提问者长期不活跃时，后续版本可增加管理员或社区共识的补充机制。

### 5.3 候选答复排序

MVP 使用可解释的排序规则：

```text
已采纳 > 有帮助反馈净值 > AI 相关性/完整度提示 > 发布时间
```

排序不是事实认证。AI 分数只用于减少跑题和广告的干扰，不直接决定答复真假。

## 6. 页面与交互设计

### 6.1 发帖/评论编辑器

新增折叠式选项：

```text
[ ] 发起问题追踪
    我希望获得的结果：________________
```

默认关闭，不干扰普通创作。勾选后提示用户描述清楚希望得到的答案、处理结果或后续信息。

### 6.2 帖子/评论详情中的问题卡片

问题卡片应显示：

- 当前状态：等待解答 / 已有结论 / 已结束；
- 问题摘要与订阅人数；
- `订阅答案` 或 `已订阅` 按钮；
- 已采纳结论的摘要、来源作者与跳转入口；
- `查看全部答复` 入口；
- AI 辅助参考及其引用来源。

仅在内容节点已开启问题追踪时展示，不能给所有帖子增加冗余的状态面板。

### 6.3 答复页

答复页分为：

1. 已采纳结论：位于顶部，显示摘要、原答复、来源和采纳时间。
2. AI 辅助参考：单独标识，显示资料来源和证据不足状态。
3. 候选答复：按排序展示，可过滤“待确认 / 已采纳 / 其他相关答复”。
4. 普通讨论：仍保持原评论层级，不把所有评论误认为答复。

### 6.4 我的问题追踪

个人主页新增固定结构的三个入口：

- 我发起的：显示状态、订阅数、待确认答复数；
- 我订阅的：显示最新结论、未读更新和来源；
- 等待我确认：优先列出存在新候选答复的问题。

## 7. 数据模型草案

```text
question
- id
- source_type                 POST / COMMENT
- source_id
- asker_id
- question_text
- status                      OPEN / COMPLETED
- accepted_answer_id
- subscriber_count
- last_answer_at
- created_at / updated_at

question_subscription
- question_id
- user_id
- last_read_answer_id
- created_at

question_answer
- id
- question_id
- comment_id                  原始评论或回复
- author_id
- status                      PENDING / ACCEPTED / REJECTED / WITHDRAWN
- ai_relevance_score          后续 AI 辅助排序字段，当前未启用
- helpful_count               后续多人反馈统计，当前未启用
- unhelpful_count             后续多人反馈统计，当前未启用
- created_at / updated_at

question_answer_feedback
- answer_id
- user_id
- feedback_type               HELPFUL / NOT_RELEVANT
- created_at

question_ai_reference
- id
- question_id
- summary
- evidence_status
- source_payload              可追溯的帖子/资料引用
- model_name / prompt_version
- created_at
```

约束：

- `(source_type, source_id)` 唯一，保证一个内容节点最多一个问题；
- `(question_id, user_id)` 唯一，保证订阅幂等；
- `(question_id, comment_id)` 唯一，防止同一条评论重复作为答复收录；
- 反馈按 `(answer_id, user_id)` 唯一，允许覆盖，不允许重复累计；
- 问题、答复与原始内容都保留必要的软删除和访问状态，避免通知与引用失效后无法解释。

## 8. 事件、通知与权限

### 8.1 领域事件

```text
QUESTION_CREATED
QUESTION_SUBSCRIBED
ANSWER_SUBMITTED
ANSWER_ACCEPTED
QUESTION_COMPLETED
QUESTION_DELETED
```

写入问题、订阅、答复或采纳状态时，与现有 Transactional Outbox 同事务写入事件；RocketMQ 消费端按 `eventId` 保持幂等。

### 8.2 通知策略

- `ANSWER_SUBMITTED`：优先通知提问者；订阅者默认不被每条候选答复打扰。
- `ANSWER_ACCEPTED`：通知所有订阅者，并携带结论摘要和答复定位信息。
- `QUESTION_COMPLETED`：发起者确认最终有效答复后通知所有订阅者，并携带结论摘要和答复定位信息。
- `QUESTION_DELETED`：发起者删除问题后通知所有订阅者，并删除对应订阅记录。
- 用户不接收由自己触发的通知。
- 通知中心后续分类为：全部、评论与回复、点赞、问题追踪、关注、收藏。

### 8.3 可见范围

- Feed、热榜、搜索推荐和 AI 检索仍按校区范围过滤。
- 从通知、个人主页或已知链接进入的内容属于互动层，可正常查看和操作已知对象。
- AI 检索问题资料时，只能查询提问者当前拥有权限访问的内容；引用不得泄露范围外帖子。

## 9. 与 RAG 和 Elasticsearch 的连接

问题追踪不是独立 UI，而是后续 AI 检索质量的来源。

1. 问题创建：将问题文本作为检索 Query，调用现有混合检索链路获取候选资料。
2. 答复采纳：把“问题 + 已采纳答复 + 证据引用 + 校园范围 + 时间”构造成高质量知识文档。
3. ES 索引：保存问题文本、状态、已采纳结论、引用内容、学校/校区、更新时间与向量。
4. RAG 排序：对于相似提问，优先召回 `COMPLETED` 状态且有来源证据的问题，再补充普通帖子。
5. 评测：除答案流畅度外，必须验证“正确历史结论是否进入 TopK”“引用是否可访问”“过期结论是否被降权”。

## 10. 分阶段开发路线

### 阶段 0：冻结设计与改造边界

- 以本文档为唯一基线，确认命名、状态机、角色和通知规则。
- 已审查并移除旧 `post_follow`、`post_progress`、`progress_status` 原型；历史迁移脚本仅保留作演进记录。
- 现有实现只作为订阅、异步事件和通知的技术验证，不再作为最终领域模型继续扩展。
- 为真实本地数据库准备从旧表到 `question` 领域模型的迁移与回滚方案。

**完成标准**：数据模型、接口草案、旧功能迁移策略和验收场景完成评审。

### 阶段 1：问题与订阅基础闭环

- 新建 `question`、`question_subscription` 与基础 API。
- 支持帖子和一级评论发起问题追踪；二级回复不创建新的问题节点。
- 支持订阅、取消订阅、问题详情和“我发起/我订阅”查询。
- 前端在内容节点中显示问题卡片与订阅状态。
- 写入事件并实现提问者、订阅者的基础通知。

**完成标准**：同一问题被多人订阅后，发起者可看到订阅数，订阅者可集中回访，权限和幂等测试通过。

### 阶段 2：候选答复与人工确认

- 新建 `question_answer`、答复反馈与答复页。
- 回复者可选择“作为答复发布”；提问者也可收录普通评论为候选答复。
- 支持采纳、待确认、不相关；发起者在至少通过一条有效答复后，可独立决定结束问题。
- 采纳后向所有订阅者发送可定位通知。
- 在个人主页展示“等待我确认”。

**完成标准**：候选答复、普通讨论、已采纳结论三者不混淆；采纳后排序、通知与统计一致。

### 阶段 3：AI 辅助与知识沉淀

- 问题创建和答复提交后触发异步 AI 任务。
- 接入带引用的 AI 辅助参考、候选答复相关性提示与违规/广告辅助检测。
- 为已采纳问题生成结论摘要，并写入 ES 文档。
- 在 RAG 中实现“已解决问题优先”的混合检索与评测集。

**完成标准**：AI 输出可追溯、无证据时会拒答；检索评测可量化说明已采纳结论的召回效果。

### 阶段 4：社区治理与体验深化

- 答复贡献记录、反滥用限制、管理员隐藏和审核流。
- 订阅偏好、通知分栏、已读管理和低打扰策略。
- 处理提问者长期不活跃时的社区共识或管理员确认机制。
- 统计解决率、平均解决耗时、高频问题和知识复用率。

**完成标准**：通知不会泛滥，异常内容可治理，核心指标可观测。

## 11. MVP 验收场景

1. 用户在帖子或评论中发起问题追踪，普通内容不出现问题卡片。
2. 两个不同用户订阅同一问题，重复订阅不重复计数。
3. 回答者提交候选答复后，仅提问者收到待确认提醒。
4. 提问者采纳答复并确认结论后，全部订阅者收到一次可定位通知。
5. 订阅者能从“我的问题追踪”进入问题、结论和原始答复。
6. 不相关答复不会排在已采纳结论之前；AI 相关性提示不会越权变成自动采纳。
7. 问题完成后不允许继续提交候选答复；发起者删除问题后，订阅者会收到删除通知且订阅记录被清理。
8. AI 返回的资料与历史答复都在当前用户可见的校园范围内，且每条引用可跳转或明确失效原因。

## 12. 当前实现的迁移原则

旧“关注进展”原型曾用于验证订阅关系、Outbox/RocketMQ 投递和通知幂等；当前版本已将其移除，统一使用问题追踪模型，避免两套相似概念同时存在。

### 阶段 2.1：多候选答复与独立结束（当前实现，优先级高于前文历史描述）

1. **答复状态**：候选答复使用 `PENDING`、`ACCEPTED`、`REJECTED`、`WITHDRAWN` 四种状态。发起者可以通过多条答复；“通过答复”只改变该答复状态，不会自动结束问题。
2. **结束与重新开启**：发起者至少通过一条答复后，才可以显式执行“结束问题”。结束后问题变为 `COMPLETED`，停止接收新的候选答复，所有已通过答复保留并作为结果集展示。发起者可将 `COMPLETED` 重新开启为 `OPEN`，保留已通过答复和订阅记录，恢复接收新的候选答复，并通知订阅者。
3. **发起者与订阅者**：发起者与订阅者是独立身份。问题结束时，系统通知所有当时订阅者；已完成问题仍允许后来者订阅并查看结果。删除问题则通知订阅者并删除其订阅记录。
4. **页面分工**：帖子问题在详情页只预览三条候选答复，评论问题后续仅预览一条；完整候选答复列表独立成页，按“已通过”和“未判断”分组。被标记无效或撤回的答复不在常规列表展示。
5. **兼容字段**：`question.accepted_answer_id` 仅为历史数据库兼容保留，结束问题时清空；新接口以 `approvedAnswerCount` 和 `approvedAnswers` 表示已通过答复集合。
6. **通知边界**：候选答复提交仅通知发起者；结束、重新开启或删除问题才通知订阅者。AI 自动提取候选答复、排序和摘要属于后续阶段，当前不替代人工判断。

### 阶段 2.2：候选答复 AI 辅助判断（当前实现）

1. 只有问题发起者可以对 `OPEN` 状态下的 `PENDING` 候选答复请求 AI 辅助判断，避免模型调用被旁观者滥用。
2. 返回内容固定为关联度分数、`RELEVANT` / `UNCERTAIN` / `IRRELEVANT` 建议和简短理由；它仅表示答复是否在回应问题，不能证明内容真实、完整或可执行。
3. 评估结果仅在候选答复页面即时展示，不修改 `question_answer` 的状态，也不触发通知、排序或积分变化。发起者仍需手动“通过答复”或“标记无效”。
4. 普通评论不会被模型自动提升为候选答复。回答者主动选择“作为候选答复发布”仍是进入答复列表的唯一入口。
5. 模拟模式用本地文本关联规则保证开发环境可测试；配置真实模型后，系统才调用模型，并且复用全局限流控制。

在阶段 1 开始前应：

1. 不再保留 `post_progress` 的 UI 和接口。
2. 将可复用的订阅、通知和事件实现下沉或迁移到 `question` 领域。
3. 为旧的本地测试数据提供一次性迁移：已关注的帖子可映射为对应的帖子问题；无法确定问题语义的旧进展记录仅保留历史或在开发环境清理。
4. 更新 API、前端契约、数据库迁移、测试和 README，避免新旧概念同时对用户暴露。

## 14. 阶段 0 审查结论（2026-08-08）

### 14.1 已验证、可复用的工程能力

历史原型曾验证下列基础能力；当前代码复用其工程模式，而不复制旧业务模型：

| 现有能力 | 当前实现 | 在问题追踪中的去向 |
| --- | --- | --- |
| 幂等订阅 | 历史原型的唯一约束与重复请求兜底 | `question_subscription(question_id, user_id)` 的唯一约束 |
| 事务事件 | `DomainEventPublisher` + Transactional Outbox | 新增 `QUESTION_*`、`ANSWER_*` 事件类型 |
| 异步投递 | Outbox Dispatcher + RocketMQ topic/consumer | 继续用于结论通知、AI 任务与 ES 索引 |
| 通知去重 | `eventId + receiverId` 生成事件键 | 继续用于每位订阅者最多收到一次同一结论通知 |
| 个人中心入口 | 历史原型的关注分页 | “我发起 / 我订阅 / 等待我确认”的固定入口 |
| 内容存在性校验 | 帖子读取、软删除判断与权限服务 | 抽取为帖子/评论的来源节点校验 |

### 14.2 不能继续沿用的旧模型

1. `post.progress_status` 只能表达整帖状态，无法承载“一个评论也可以是问题”的产品要求。
2. 历史订阅模型只能订阅帖子，不能唯一定位帖子、一级评论或二级回复中的问题节点。
3. 历史进展模型仅允许帖主或管理员发布，和“任意用户提交候选答复”的协作模式冲突。
4. `UPDATE / RESOLVED` 把“发布者更新”和“提问者采纳结论”混为一件事；前者是事件，后者才是问题状态变化。
5. `POST_PROGRESS_PUBLISHED` 事件只有 `postId` 与文本，不能表达来源评论、候选答复、采纳人、结论和引用。
6. 旧前端进展面板仅面向帖子，继续保留会让用户看到两套相似但不一致的概念。

因此，旧表和接口在阶段 1 后不再向新页面暴露；它们只保留到数据迁移与回归验证结束，随后再单独安排清理。

### 14.3 安全迁移策略

阶段 1 的数据库迁移使用新增而非替换的方式：

1. 新建 `question` 和 `question_subscription`，并在切换后移除旧业务模型。
2. 现有进展测试数据不自动转换为问题，因为旧记录没有可靠的“问题文本”和“发起者意图”；本地开发可在手动发起问题后，按需把旧关注关系映射到新订阅关系。
3. Vue 页面与 API 只使用 `/api/questions`；用户不会看到旧的“关注进展”概念。
4. 待问题、订阅和候选答复链路的集成测试稳定后，再将旧接口标记为废弃，并另行执行数据清理迁移。

### 14.4 阶段 1 的接口契约

阶段 1 只完成“问题对象 + 订阅”闭环，不提前混入候选答复、AI 判断或积分。

```text
POST   /api/questions
       创建问题追踪：sourceType、sourceId、questionText

GET    /api/questions/by-source?sourceType=POST|COMMENT&sourceId={id}
       读取某个帖子或评论节点的问题卡片；不存在时返回空结果

GET    /api/questions/{questionId}
       读取问题详情、状态、发起者、订阅人数和当前用户订阅状态

POST   /api/questions/{questionId}/subscriptions
DELETE /api/questions/{questionId}/subscriptions
       幂等订阅与取消订阅

GET    /api/users/me/questions?role=ASKED|SUBSCRIBED
       个人中心的“我发起 / 我订阅”列表

阶段 1 不提供直接修改问题状态的客户端接口；阶段 2 仅允许通过采纳有效答复将问题标记为完成。
```

来源节点校验规则：`sourceType=POST` 时校验正常帖子；`sourceType=COMMENT` 时校验正常评论，并从评论反查所属帖子。创建、订阅、查看与个人列表均须沿用内容可见性和软删除规则。

### 14.5 阶段 1 完成前不得省略的测试

1. 同一帖子或评论节点只能创建一个问题，重复创建返回冲突。
2. 发起者和订阅者是独立身份：发起者不可订阅自己的问题，其他可见用户可订阅；重复订阅不会重复计数。
3. 取消订阅后计数正确，重复取消保持幂等。
4. 已删除帖子/评论不能创建、订阅或读取新问题。
5. 阶段 1 不提供直接关闭问题的入口；“已完成”必须等阶段 2 的有效答复采纳后产生。
6. “我发起”和“我订阅”分页列表互不混淆，且不会泄露当前用户无权访问的来源内容。
7. 新 API、数据库迁移、事务边界和前端关键交互均有自动化回归；旧进展功能在迁移期间仍能被独立回归验证。

## 16. 订阅生命周期规则（2026-08-08 确认）

本节优先级高于此前任何“关闭问题”或“关闭即清空订阅”的描述。

### 16.1 角色边界

- **发起者**：创建问题的来源内容作者。发起者管理问题是否完成，也可以删除问题；发起者不属于订阅者，不显示“订阅答案”入口。
- **订阅者**：对该问题的结果感兴趣的其他用户。订阅者只能管理自己的订阅，可以在任意阶段取消订阅，不能改变问题状态或删除问题。
- **回答者**：下一阶段引入。回答者提交候选答复，但不能自行宣布问题完成。

### 16.2 状态与订阅规则

| 问题状态 | 含义 | 发起者 | 订阅者 | 未订阅用户 |
| --- | --- | --- | --- | --- |
| `OPEN`（进行中） | 尚未确认最终有效答复 | 等待、筛选和采纳候选答复 | 接收最终结果，可取消订阅 | 可订阅 |
| `COMPLETED`（已完成） | 发起者已确认最终有效答复 | 可查看结论或删除问题 | 保留订阅，可查看结果或取消订阅 | 仍可订阅，并立即获得结果 |

完成问题绝不清空 `question_subscription`。订阅者个人中心需固定分为“进行中”和“已完成”两个栏目，两个栏目中都可执行取消订阅。

### 16.3 生命周期事件

1. 发起者创建问题后，问题进入 `OPEN`；其他用户可订阅。
2. 回答者提交候选答复后，仅发起者收到待确认提醒；订阅者不因每一条候选答复被打扰。
3. 发起者确认一条有效答复时，系统将问题设为 `COMPLETED`，向全部当前订阅者发送一次包含最终答复定位和摘要的通知。
4. 后续用户仍可订阅已完成问题，系统立即提供已确认答复；该订阅记录进入其“已完成”栏目。
5. 发起者删除问题时，系统向全部订阅者发送“问题已删除”通知，再清理 `question_subscription`；用户的订阅列表不再保留失效记录。

旧版“关闭追踪 / 重新开启”已移除；阶段 2 改为围绕候选答复的“结束问题 / 重新开启问题”。结束与重新开启均由发起者显式执行，状态改变与答复、订阅和通知保持一致。

## 17. 当前实现状态（2026-08-08）

本节优先级高于文中较早的“下一阶段”描述，用于区分已上线能力与后续规划。

### 17.1 已实现的基础闭环

1. `question` 支持 `OPEN` 与 `COMPLETED` 两个状态；发起者不是订阅者，不能订阅自己的问题。
2. 其他用户可在进行中或已完成状态订阅；已完成问题的新订阅者会直接看到已采纳的最终答复。订阅者可在两个栏目中取消订阅。
3. 回答者在发布真实评论或直接回复时，可同时勾选“作为候选答复”。系统保存评论本身，再创建 `question_answer` 记录，不复制答复文本。
4. 帖子问题允许其下评论作为候选答复；评论问题只允许其直接回复作为候选答复，避免答案脱离原问题语境。
5. 候选答复初始为 `PENDING`。只有问题发起者能采纳或标记无效；采纳会在同一业务链路中写入最终答复、把问题改为 `COMPLETED`，并通知所有当时的订阅者。
6. 候选答复提交只通知发起者；发起者删除问题时，系统先向订阅者发送删除通知，再清理答复和订阅记录。答复作者可删除自己的候选答复，删除会撤回候选资格；若删除的是已完成问题的最后一条已通过答复，系统自动将问题恢复为进行中并通知订阅者。
7. 生命周期事件通过 Transactional Outbox 与 RocketMQ 投递，通知消费者按事件幂等写入，避免事务提交与异步通知脱节。

### 17.2 当前边界与后续工作

1. Vue 页面已覆盖帖子与评论来源的问题、订阅、候选答复列表、采纳、标记无效和个人订阅的进行中/已完成分栏；评论问题会聚合展示在所属帖子的问题区域，并保留评论旁的状态与入口；仅一级评论作者可发起新的评论问题。
2. 候选答复的“无效/待定/有效”多方反馈、回答者信誉分和排序规则尚未实现；当前仅有发起者的采纳或标记无效操作。
3. AI 只在后续阶段对已采纳答复、引用内容做摘要与证据校验，不能替代发起者确认最终结果。
4. 旧的 `post_progress` 与 `post_follow` 已从运行时代码移除，不再作为新版问题追踪的产品入口或状态来源。

## 18. 当前候选答复与结束问题规则（2026-08-09）

本节优先级高于文档中所有“采纳单条答复后自动完成问题”或“最终答复唯一”的历史描述。

1. 候选答复拥有 `PENDING`、`ACCEPTED`、`REJECTED` 三种状态。提问发起者可以通过多条候选答复；通过一条答复只改变该答复的状态，不会关闭问题。
2. 问题保持 `OPEN` 时，符合来源范围的评论或回复仍可继续作为候选答复提交。发起者在至少通过一条答复后，才能执行“结束问题”。
3. “结束问题”会将问题改为 `COMPLETED`，停止接收新的候选答复，并向当时的订阅者发送完成通知。已通过的全部答复均保留，作为该问题的结果集合；问题本身并未被删除。
4. 只有发起者可以将 `COMPLETED` 重新开启为 `OPEN`。重新开启不删除已通过答复或订阅记录，问题会再次接收候选答复，并向订阅者发送重新开启提醒。
5. 帖子详情页只展示最多三条候选答复；评论来源的问题在评论旁展示状态和候选答复入口，完整内容统一通过“查看全部候选答复”进入专用页面。
6. 专用候选答复页面分为“已通过”和“未判断”两个分组；已拒绝答复不在普通浏览列表中展示。发起者仅能在问题处于 `OPEN` 时对未判断答复进行通过或标记无效。
7. 发起者与订阅者是独立身份：发起者控制结束、重新开启或删除问题；订阅者可以随时取消订阅。问题结束后，订阅记录依然保留在“已完成”栏目中，后续用户也可订阅并直接查看全部已通过答复。
