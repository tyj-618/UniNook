# CampusCircle 产品闭环审查与实施清单

## 审查目标

本次审查以真实用户从注册到持续使用的完整路径为单位，而不是仅检查单个接口是否可调用。校园归属和附近学校范围是 CampusCircle 的核心发现边界：附近 Feed、热门/搜索推荐和 AI 检索必须遵守该边界；通知、详情、评论、点赞和个人主页等已知内容入口应保证可正常互动。

后续需求、优先级与验收标准统一维护在 [development-roadmap.md](development-roadmap.md)。

## 文档状态

本文保留为早期闭环审查记录，其中“发现的闭环缺口”和“本轮实施范围”反映的是当时的基线，部分事项已经在后续迭代中完成。新的需求状态、范围规则和实施顺序以开发路线图为准。

## 后续优化原则

用户提出的产品优化一律按端到端能力处理，而不是孤立的前端改动。每项需求至少审查以下层面：

- 数据模型与历史数据迁移。
- API 契约、服务端业务规则与权限边界。
- 缓存、消息事件、搜索索引或统计数据的同步影响。
- 前端信息架构、交互状态和移动端呈现。
- 单元测试、集成测试、验收场景与文档。

只有这些层面共同闭环后，需求才视为完成。

## 已具备的后端能力

- 注册、登录、Token 会话管理。
- 学校搜索、附近学校计算和 Redis 缓存。
- 帖子、评论、点赞、通知、后台管理。
- 附近学校 Feed、游标分页、热榜与浏览量处理。
- 基于附近学校范围的 RAG 问答、模型调用限流与成本控制。
- Docker Compose 本地运行环境。

## 发现的闭环缺口

### P0：学校归属被静默写为默认值

`user.school_id` 当前使用默认值 `1`。注册时并不收集学校，因此新用户会被错误归属到种子学校。该行为会直接影响 Feed、发帖归属、详情权限和 AI 检索范围。

**修复原则：** 新用户允许处于“待绑定学校”状态；所有依赖学校归属的业务必须明确要求已绑定学校；前端首次登录进入学校选择页。

### P0：核心前端用户路径不完整

当前前端已经覆盖登录、注册、Feed、帖子详情、点赞和评论，但缺少：

- 学校选择与后续修改。
- 发帖页面。
- 个人资料页面。
- 站内通知页面。
- AI 问答页面。

这些能力已经有后端基础，应该以现有接口为边界补齐，不额外引入不必要的前端状态管理框架。

### P0：部分旧查询接口没有范围保护

`GET /api/posts`、`GET /api/posts/hot`、`GET /api/users/{userId}/posts` 的原设计可查询全量帖子。它们必须改为认证后按当前用户的学校范围查询，或在没有实际产品用途时不向前端暴露。

### P1：首次登录状态不完整

登录响应仅含用户摘要，前端登录后没有立即刷新完整资料，导致无法可靠判断学校是否已绑定。登录完成后必须调用 `GET /api/users/me`，再决定进入学校选择页或 Feed。

### P1：可验证性不足

现有集成测试覆盖了部分认证、互动与范围拒绝场景，但缺少：

- 新用户未绑定学校时不能浏览、发帖和调用 AI。
- 完成学校绑定后可以进入 Feed 并发帖。
- 全局列表和热门列表不会泄露范围外帖子。
- 用户资料更新后，后续请求使用新的学校归属。

## 本轮实施范围

1. **学校绑定闭环**：数据库、用户资料查询、后端业务校验、前端路由守卫与学校选择页。
2. **基础创作闭环**：分类读取、发帖页、Feed 入口与发布成功回流。
3. **个人中心闭环**：查看和编辑昵称、简介、学校。
4. **互动与通知闭环**：通知列表、未读数、单条和全部已读。
5. **AI 可见能力**：问答页、引用跳转、无证据状态和调用失败提示。
6. **范围权限收口**：移除或收紧所有可绕开附近学校范围的帖子查询。
7. **验证与交接**：补集成测试，执行后端测试和前端 lint/build，提供按用户旅程组织的验收清单。

## 不在本轮提前实现的内容

- **输入与操作反馈统一优化（下一轮视觉交互）**：输入框、下拉框、文本域在 hover、focus、填写有效、校验失败、保存中和保存成功时提供明确且克制的视觉反馈；按钮需要有禁用、提交中与成功结果状态。该项与布局优化统一进行，不改变当前业务接口。
- **个人主页与资料完善（下一轮功能）**：个人中心拆分为“资料编辑”和“个人主页”。主页展示头像、昵称、账号 ID、学校、简介、公开帖子与互动概览；资料设置增加每项资料的公开范围控制。头像上传需要在部署阶段一并确定对象存储和内容安全方案，当前先保留头像 URL 字段。
- **作者主页跳转（下一轮功能）**：帖子和评论中的头像、昵称均可进入作者主页。后端需将公开主页与帖子列表都纳入附近学校范围校验，避免通过用户 ID 绕过校园可见范围。
- **我的互动记录（下一轮功能）**：个人中心增加“我的帖子 / 我的评论 / 我的点赞”入口，并可跳转到原帖子。评论查询接口已具备基础；点赞记录需要新增用户维度的查询接口、分页与范围过滤。
- **评论能力完善（下一轮功能）**：
  - 当前用户自己的评论展示删除入口，并复用现有删除接口；删除后同步刷新帖子评论数和列表状态。
  - 支持二级回复，但不允许无限嵌套。数据模型增加 `root_comment_id`、`parent_comment_id` 和 `reply_to_user_id`：顶级评论的 `root_comment_id` 为空；任何对二级评论的再次回复仍归入同一顶级评论下，以“回复某用户”的形式展示。
  - 评论响应增加作者学校/校区展示字段，并将学校信息设计为可复用的视觉标签。评论读取、创建和删除继续复用附近校园范围权限校验。
- **社交关系与私聊（长期评估）**：关注、好友和私聊需先确定单向/双向关系、陌生人策略、拉黑、举报、消息未读数、频率限制、内容审核和隐私边界。它们会引入新的数据模型与安全责任，在完成基础社区和部署后再评估是否进入项目范围。
- **学校选择体验升级**：学校绑定页后续改为“省份 -> 城市 -> 学校”的级联选择，并保留关键词搜索作为快速筛选入口。需要先扩充学校数据集，并增加按省份、城市查询的接口或聚合数据接口。
- **校区级地理模型与范围筛选升级（后续核心功能）**：用户的实际归属应从“学校”细化为“校区”，例如同一高校的不同校区拥有独立经纬度、地址与内容范围。数据模型建议拆分为 `university`（高校）与 `campus`（校区），帖子归属 `campusId`，用户绑定 `campusId`；展示时仍可显示高校名称和校区名称。
- **范围选项重构（随校区模型一起实施）**：Feed 和 AI 检索统一支持 `同校区`、`同校`、`10 km`、`20 km`、`同市`。其中“同校”与“同校区”分别由高校和校区标识确定；`10/20 km` 基于当前校区坐标计算；“同市”按当前校区所属城市过滤，不应伪装为超大半径。所有范围仍由服务端依据 Token 推导当前校区后执行，前端仅传递范围枚举值。
- Elasticsearch 向量混合检索已落地：下一步使用真实 Embedding 模型建立评测集，并验证索引收敛、TopK 命中与 SQL 降级。
- 管理后台 UI：后端管理接口保留，普通用户端不应出现管理入口。
- 文件上传、私信、审核工作流：需先单独定义对象存储、内容安全和产品规则。
